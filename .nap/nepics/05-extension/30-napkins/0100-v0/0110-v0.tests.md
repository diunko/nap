# v0 — lifecycle tests

## Why this exists

`0100-v0.test.md` tests seams in isolation — Monaco boots, LFS reads/writes, nav tree parses conventions. Those catch wiring bugs.

But the extension's reason to exist is a **two-repo bridge**: you're on `github.com/org/main-repo` reading a PR, and the side panel shows .nap content from a *different* repo. File:line links in .nap chapters point back to main-repo. That full loop — clone .nap, read chapter, click link, land on the right line in the right repo — is what "working" means.

The seam tests prove parts work. These tests prove the *thing* works.

---

## Test infrastructure (proven by spikes)

### Playwright + real side panel

Spikes confirmed: Playwright can open the real Chrome side panel and interact with it.

**Required env var:** `PW_CHROMIUM_ATTACH_TO_OTHER=1` — set before creating browser context. Chrome reports side panels as CDP target type `"other"`; this flag makes Playwright treat them as Page objects.

**Opening the panel:**
1. Content script injects a trigger button (`#nap-open-panel`, near-invisible) on github.com
2. Playwright clicks it
3. Content script sends `chrome.runtime.sendMessage({ type: 'open_side_panel' })`
4. Service worker calls `chrome.sidePanel.open({ tabId: sender.tab.id })`
5. Playwright catches the panel via `context.waitForEvent('page', { predicate: p => p.url().includes('side-panel.html') })`

**Critical validation:** from the real side panel, `chrome.tabs.query({ active: true, currentWindow: true })` returns the GitHub tab. This matches production semantics — the panel can navigate the main tab via `chrome.tabs.update(tabId, { url })`.

**Chrome launch args:**
```typescript
args: [
  `--disable-extensions-except=${pathToExtension}`,
  `--load-extension=${pathToExtension}`,
  '--disable-blink-features=AutomationControlled',  // prevents github.com captcha
]
```

**Extension ID:** derived from service worker URL: `context.serviceWorkers()[0].url().split('/')[2]`

### Content script on github.com

Spikes confirmed: content script injects on github.com without CSP blocks or captcha issues.

Both messaging paths work:
- `chrome.tabs.update(tabId, { url })` — navigates GitHub tab directly from side panel (simpler)
- `chrome.tabs.sendMessage(tabId, msg)` → content script `onMessage` → `window.location.href` — full content-script-in-the-loop chain

### Monaco CSP

Spikes confirmed: working CSP config is `script-src 'self' 'wasm-unsafe-eval'; worker-src 'self';` (no `blob:` needed).

### Fixture pattern

```typescript
// fixtures.ts
process.env.PW_CHROMIUM_ATTACH_TO_OTHER = '1';

// Test setup: navigate to github.com, open real side panel
const githubPage = await context.newPage();
await githubPage.goto('https://github.com/org/nap-test-main');
const panelPage = await openSidePanel(context, githubPage, extensionId);
await panelPage.waitForSelector('.monaco-editor');
await panelPage.waitForSelector('.wterm');
```

## Fixture repos

Two real public repos on GitHub, pre-populated by the test engineer:

**`nap-test-main`** — emulates the main code repo
  * has real files at known paths with known content
  * `modules/server/copy_document.ts` — at least 60 lines, line 51 has a recognizable marker comment
  * `modules/core/id_universe.ts` — at least 20 lines, line 12 has a marker
  * `README.md`
  * never cloned by the extension — only linked via GitHub blob URLs

**`nap-test-nap`** — emulates the .nap repo
  * `.nap/` directory with full conventions:
    * `20-architects/001-architect/` (prompt.md)
    * `30-napkins/0100-feature/` (.napkin.nap.json status "doing", agents/)
    * `30-napkins/0200-other/` (.napkin.nap.json status "backlog")
  * mini-book chapters under 0100-feature:
    * `01-copy-pipeline.md` — contains file:line links pointing at nap-test-main
    * `02-id-universe.md` — contains file:line links + relative .md link back to 01
  * cloned into IDB by the extension terminal

**Main-repo config** — stored in `chrome.storage.sync` via the extension popup. User pastes `org/nap-test-main` once. All file:line links resolve against it.

For Playwright tests, pre-set via `page.evaluate`:
```typescript
const MAIN_REPO = 'org/nap-test-main';
const MAIN_BRANCH = 'main';
const NAP_REPO_URL = 'https://github.com/org/nap-test-nap';

// Set main-repo config before tests that need link routing
await panelPage.evaluate((repo) => {
  chrome.storage.sync.set({ mainRepo: repo });
}, MAIN_REPO);
```

For manual testing, user sets the same value through the extension popup.

## Lifecycle tests

All lifecycle tests are **medium** (Playwright + real Chrome extension + real side panel + real github.com).

### L1 — first session: clone .nap, read chapter, click through to code

* **flow:**
  1. Playwright navigates to `github.com/org/nap-test-main` (the code repo the user is reviewing)
  2. open real side panel via trigger button pattern
  3. set main-repo config: `chrome.storage.sync.set({ mainRepo: 'org/nap-test-main' })`
  4. terminal: `git clone https://github.com/org/nap-test-nap`
  5. call `window.__refreshNavTree()` (explicit refresh after clone)
  6. nav tree shows 0100-feature (doing), 0200-other (backlog)
  7. click `01-copy-pipeline.md` → editor opens, napkin-markdown tokenized
  8. chapter contains `[copy_document.ts:51](/modules/server/copy_document.ts#L51)`
  9. Cmd+click → side panel sends `chrome.tabs.update(tabId, { url })` → GitHub tab navigates to `https://github.com/org/nap-test-main/blob/main/modules/server/copy_document.ts#L51`
* **what it proves:** the two-repo bridge works end-to-end. Clone from repo A, link resolves to repo B, GitHub tab actually navigates.
* **where it breaks:** main-repo config not read by link router, URL constructed with .nap repo owner instead of main repo owner, `chrome.tabs.update` fails or targets wrong tab, #L51 anchor dropped.
* **verification:**
  * assert nav tree DOM contains "0100-feature" and "doing" label
  * assert editor model contains expected chapter content
  * assert `githubPage.url()` ends with `/copy_document.ts#L51` after Cmd+click

### L2 — review cycle: read, comment, commit

* **flow:**
  1. (continues from L1 state — repo cloned, chapter open)
  2. type `//DU: this looks fragile` in Monaco editor
  3. wait auto-save (poll LFS until content matches)
  4. switch to terminal tab
  5. `cd nap-test-nap && git status` → shows modified `01-copy-pipeline.md`
  6. `git add .`
  7. `git commit -m "review: copy pipeline"` → shows commit hash
  8. `git log --oneline -1` → shows "review: copy pipeline"
* **what it proves:** the edit → save → git cycle works with the shared LFS instance. Editor writes are visible to git.
* **where it breaks:** auto-save path mismatch (editor writes to wrong location relative to git root), git status computes from HEAD but the file path in the working tree doesn't match.
* **verification:**
  * cmd() helper on panelPage for terminal assertions (extend bash-poc pattern)
  * `panelPage.evaluate(() => window.__lfs.promises.readFile(path, 'utf8'))` to verify auto-save before terminal step

### L3 — navigation loop: .nap → code → .nap → code

* **flow:**
  1. editor showing `01-copy-pipeline.md`
  2. Cmd+click `02-id-universe.md` (relative .md link) → editor loads 02 from IDB (stays in side panel)
  3. `02-id-universe.md` has `[id_universe.ts:12](/modules/core/id_universe.ts#L12)`
  4. Cmd+click → GitHub tab navigates to `nap-test-main/blob/main/modules/core/id_universe.ts#L12`
  5. `02-id-universe.md` also links back to `01-copy-pipeline.md`
  6. Cmd+click → editor loads 01 again
* **what it proves:** routing switch works repeatedly — .md stays local, file:line goes to GitHub, .md stays local again. No state corruption from alternating.
* **where it breaks:** editor model cache returns stale content on re-open, routing logic misclassifies a link after the first navigation, `chrome.tabs.update` fails after tab has already navigated once.
* **verification:**
  * after step 2: assert editor model value contains 02's content
  * after step 4: assert `githubPage.url()` contains `id_universe.ts#L12`
  * after step 6: assert editor model value contains 01's content again

### L4 — tab reuse for code links

* **flow:**
  1. Cmd+click `copy_document.ts:51` → GitHub tab navigates
  2. Cmd+click `id_universe.ts:12` → same tab updates (single-click reuses tab via `chrome.tabs.update`)
* **what it proves:** all code links reuse the GitHub tab. No tab explosion.
* **where it breaks:** `chrome.tabs.update` called with wrong tabId after first navigation, new tab created instead of reusing.
* **verification:**
  * count `context.pages()` before and after each click — no new pages created
  * assert `githubPage.url()` updates to each target
* **NOTE:** double-click → new tab dropped from v0. Single-click-reuses only.

### L5 — panel survives browsing

* **flow:**
  1. panel open, repo cloned, chapter in editor, terminal has history
  2. file:line click → GitHub tab goes to blob page
  3. navigate GitHub tab to a different URL: `githubPage.goto('https://github.com/org/nap-test-main/tree/main/modules')`
  4. navigate again: `githubPage.goto('https://github.com/org/nap-test-main')`
  5. check panel: editor still has same content, terminal history still present, nav tree still populated
  6. Cmd+click another file:line from panel → GitHub tab navigates again
* **what it proves:** panel state is independent of main tab navigation. In-memory state survives.
* **where it breaks:** Chrome destroys side panel DOM when main tab navigates between github.com pages. If DOM is destroyed, Monaco models and terminal history are lost.
* **verification:**
  * after step 5: assert `panelPage.evaluate(() => window.__editor.getModel().getValue())` still contains expected content
  * after step 5: assert terminal DOM still contains command history
  * after step 6: assert `githubPage.url()` changed to new target
* **RISK:** if Chrome destroys/recreates the panel DOM on tab navigation, this test will fail. That's a real Chrome behavior we can't control. If it fails, the fallback is: rebuild all state from IDB on panel re-creation (heavier but workable), and this test becomes a verification that the rebuild works correctly.

### L6 — return visit (IDB persistence)

* **flow:**
  1. clone repo, open a chapter, make an edit, commit (reuse L2 setup)
  2. close side panel (navigate GitHub tab away from github.com, or close it)
  3. navigate back to `github.com/org/nap-test-main`
  4. reopen side panel via trigger button
  5. call `window.__refreshNavTree()` — nav tree reads from existing IDB, no re-clone
  6. open same chapter → content includes the committed edit
* **what it proves:** `'nap-ext'` store name is stable, IDB survives panel close/reopen, nav tree can populate from existing data.
* **where it breaks:** LFS store name different on reopen (unlikely — same hardcoded name), nav tree startup path only handles fresh state (no "IDB already has data" path).
* **verification:**
  * after step 5: assert nav tree DOM contains expected structure
  * after step 6: assert editor model value includes the edit from step 1

## What's missing from 0100-v0.test.md that these expose

1. **Content script ↔ side panel messaging** — the side panel calls `chrome.tabs.update(tabId, { url })` to navigate the GitHub tab. No seam test covers this cross-context boundary.

2. **Main-repo config resolution** — `{owner}/{repo}` flows from `chrome.storage.sync` into the link URL builder. Seam tests test link parsing in isolation but never with the actual config source.

3. **Multi-step state accumulation** — L2 depends on L1's clone. L3 depends on L2's editor state. Real bugs live in accumulated state, not fresh-start isolation.

4. **Real GitHub tab interaction** — content script running on github.com, tab navigation visible and assertable. Not tested at all in seam tests.

## Resolved questions

### Q1: main-repo config → chrome.storage.sync via popup

User sets `{owner}/{repo}` in extension popup. Stored in `chrome.storage.sync`. Link router reads it. Tests pre-set via `page.evaluate`. Manual testing uses the same popup.

### Q2: content script testing → fully automatable

Spikes proved: content script injects on github.com, messaging works both ways, `chrome.tabs.update` navigates the tab. All lifecycle tests run against real github.com with `--disable-blink-features=AutomationControlled`.

### Q3: tab reuse → single-click-reuses only for v0

Double-click → new tab dropped. All code links reuse the same GitHub tab via `chrome.tabs.update`.

### Q4: nav tree refresh → explicit `window.__refreshNavTree()`

No filesystem watcher. Nav tree refreshes when: (a) explicitly called after clone/pull, (b) on panel startup (reads existing IDB). Tests call it explicitly after relevant operations.

### Q5: fixture repo ownership

Public repos, TE creates and maintains. Content is deterministic — specific files at specific line numbers with marker comments. TE creates before test implementation begins.

## Remaining manual-only test

**Panel lifecycle on tab navigation (spike 4):** does Chrome destroy/recreate the side panel DOM when the main tab navigates? This depends on real Chrome side panel frame behavior that can't be observed through Playwright's page handle. Must be tested manually: open panel, start a counter, navigate main tab, check if counter resets.

This answer determines whether L5 passes or needs a rebuild-from-IDB fallback. If DOM is destroyed, L6 becomes critical (IDB persistence is the only continuity path).
