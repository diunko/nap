# v0 — lifecycle tests

## Why this exists

`0100-v0.test.md` tests seams in isolation — Monaco boots, LFS reads/writes, nav tree parses conventions. Those catch wiring bugs.

But the extension's reason to exist is a **two-repo bridge**: you're on `github.com/org/main-repo` reading a PR, and the side panel shows .nap content from a *different* repo. File:line links in .nap chapters point back to main-repo. That full loop — clone .nap, read chapter, click link, land on the right line in the right repo — is what "working" means.

The seam tests prove parts work. These tests prove the *thing* works.

## Fixture repos

Two real public repos on GitHub, pre-populated by the test engineer:

**`nap-test-main`** — emulates the main code repo
  * has real files at known paths with known content
  * `modules/server/copy_document.ts` — at least 60 lines, line 51 has a recognizable marker comment
  * `modules/core/id_universe.ts` — at least 20 lines, line 12 has a marker
  * `README.md`
  * never cloned by the extension — only linked via GitHub blob URLs

**`nap-test-nap`** — emulates the .nap repo
  * `.nap/` directory with full conventions:
    * `20-architects/001-architect/` (prompt.md)
    * `30-napkins/0100-feature/` (.napkin.nap.json status "doing", agents/)
    * `30-napkins/0200-other/` (.napkin.nap.json status "backlog")
  * mini-book chapters under 0100-feature:
    * `01-copy-pipeline.md` — contains file:line links pointing at nap-test-main
    * `02-id-universe.md` — contains file:line links + relative .md link back to 01
  * cloned into IDB by the extension terminal

**Link target parameter** — how the extension knows file:line links should resolve to nap-test-main, not nap-test-nap. Manual config:

```
nap config set main-repo org/nap-test-main
```

Or a setting in the extension popup. Or a file in the .nap repo. TBD — but the contract is: the user provides `{owner}/{repo}` once, and all file:line links use it.

For Playwright tests, both repos are configured in the test fixture:

```typescript
const MAIN_REPO = 'org/nap-test-main';
const MAIN_BRANCH = 'main';
const NAP_REPO_URL = 'https://github.com/org/nap-test-nap';
```

For manual testing, the user sets the same value through whatever UI exists.

## Lifecycle tests

### L1 — first session: clone .nap, read chapter, click through to code

* **flow:**
  1. side panel loads (via chrome-extension:// URL in tests)
  2. terminal: `git clone <NAP_REPO_URL>`
  3. set main-repo target: `nap config set main-repo org/nap-test-main` (or equivalent)
  4. nav tree shows 0100-feature (doing), 0200-other (backlog)
  5. click `01-copy-pipeline.md` → editor opens, napkin-markdown tokenized
  6. chapter contains `[copy_document.ts:51](/modules/server/copy_document.ts#L51)`
  7. Cmd+click → main tab navigates to `https://github.com/org/nap-test-main/blob/main/modules/server/copy_document.ts#L51`
* **what it proves:** the two-repo bridge works end-to-end. clone from repo A, link resolves to repo B.
* **where it breaks:** main-repo config not read by link router, URL constructed with .nap repo owner instead of main repo owner, content script doesn't receive navigation message, #L51 anchor dropped.

### L2 — review cycle: read, comment, commit

* **flow:**
  1. (continues from L1 state — repo cloned, chapter open)
  2. user types `//DU: this looks fragile` in editor
  3. wait auto-save
  4. switch to terminal
  5. `cd nap-test-nap && git status` → shows modified `01-copy-pipeline.md`
  6. `git add .`
  7. `git commit -m "review: copy pipeline"` → shows commit hash
  8. `git log --oneline -1` → shows "review: copy pipeline"
* **what it proves:** the edit → save → git cycle works with the shared LFS instance. Editor writes are visible to git.
* **where it breaks:** auto-save path mismatch (editor writes to wrong location relative to git root), git status computes from HEAD but the file path in the working tree doesn't match.

### L3 — navigation loop: .nap → code → .nap → code

* **flow:**
  1. editor showing `01-copy-pipeline.md`
  2. Cmd+click `02-id-universe.md` (relative .md link) → editor loads 02 from IDB (stays in side panel)
  3. `02-id-universe.md` has `[id_universe.ts:12](/modules/core/id_universe.ts#L12)`
  4. Cmd+click → main tab navigates to nap-test-main's `id_universe.ts#L12`
  5. `02-id-universe.md` also links back to `01-copy-pipeline.md`
  6. Cmd+click → editor loads 01 again
* **what it proves:** routing switch works repeatedly — .md stays local, file:line goes to GitHub, .md stays local again. No state corruption from alternating.
* **where it breaks:** editor model cache returns stale content on re-open, routing logic misclassifies a link after the first navigation, content script loses connection after tab navigation.

### L4 — tab behavior for code links

* **flow:**
  1. Cmd+click `copy_document.ts:51` → main tab navigates to GitHub blob
  2. Cmd+click `id_universe.ts:12` → same tab updates (reuses — single click)
  3. Cmd+double-click `schema.ts:99` → new tab opens
* **what it proves:** tab reuse policy — single click reuses, double click opens new
* **where it breaks:** content script doesn't distinguish single vs double click, `chrome.tabs.update` vs `chrome.tabs.create` logic wrong, tab ID tracking lost after first navigation.
* **NOTE:** double-click detection in Monaco may be hard. If Cmd+double-click isn't feasible, drop to single-click-reuses-tab only. Flag for architect.

### L5 — panel survives browsing

* **flow:**
  1. panel open, repo cloned, chapter in editor, terminal has history
  2. file:line click → main tab goes to GitHub blob
  3. user browses GitHub (clicks function, navigates to another file — main tab URL changes multiple times)
  4. switch back to panel — editor still has same content, terminal still has history, nav tree still populated
  5. Cmd+click another file:line from panel → main tab navigates again
* **what it proves:** panel state is independent of main tab navigation. IDB persists, in-memory state (Monaco models, terminal) survives.
* **where it breaks:** Chrome destroys side panel DOM on tab navigation (known behavior in some contexts), Monaco models gc'd, terminal loses history because shell state was in-memory.
* **NOTE:** testing via chrome-extension:// URL may not reproduce real side panel lifecycle. If untestable automatically, mark as manual-only.

### L6 — return visit (IDB persistence)

* **flow:**
  1. clone repo, open a chapter, make an edit, commit
  2. close panel (or navigate away and back)
  3. reopen panel → IDB still has cloned repo
  4. nav tree repopulates without re-clone
  5. open same chapter → content includes the committed edit
* **what it proves:** `'nap-ext'` store name is stable, IDB survives panel close/reopen, no ephemeral state required for basic read.
* **where it breaks:** LFS creates new store on panel reopen (different instance, same name — should work, but verify), nav tree doesn't read on startup (waits for clone event that never comes).

## What's missing from 0100-v0.test.md that these expose

1. **Content script ↔ side panel messaging** — the side panel sends "navigate to this GitHub URL" and the content script on github.com receives it and calls `chrome.tabs.update`. No seam test covers this message-passing boundary.

2. **Main-repo config resolution** — how `{owner}/{repo}` flows from user config into the link URL builder. The seam tests test link parsing in isolation but never with the actual config source.

3. **Multi-step state accumulation** — L2 depends on L1's clone. L3 depends on L2's editor state. Real bugs live in accumulated state, not fresh-start isolation.

4. **Content script on github.com** — a script running on the actual github.com page that receives messages and manipulates the tab. Not tested at all in seam tests.

## Open questions

### Q1: how does the extension know which main repo to link to?

The spec says file:line resolves to `{owner}/{repo}` of the main code repo. But how does the extension get that value?

Options:
* **manual parameter** — user types `nap config set main-repo org/repo` in terminal, or sets it in extension popup. Simplest. Works for v0. ← current assumption for tests
* **file in .nap repo** — e.g. `.nap/config.json` with `{ "mainRepo": "org/repo" }`. Cloned with the repo, no extra step.
* **detect from GitHub page URL** — content script reads `github.com/{owner}/{repo}` from the main tab and infers it. Fragile — what if user navigates to a different repo?

For tests: we go with manual parameter. Tests set it via fixture config. User sets it the same way for manual testing.

**Needs architect decision before fs-eng starts.**

### Q2: content script testing strategy

The content script runs on github.com, not in the extension page. Playwright can load the extension, but can the test:
* navigate to a real github.com page with the extension loaded?
* verify the content script received a message from the side panel?
* assert the main tab URL changed?

If yes → L1 and L3 are fully automatable.
If no → we need a mock: content script logic tested in isolation, message format tested in a small test, actual github.com interaction is manual.

**Needs TE spike before writing test implementations.**

### Q3: tab reuse — single vs double click

The napkin says: `.ts/.tsx → GitHub blob, single-click reuses tab, double-click opens new`. Monaco's click handling may not expose double-click on links cleanly. Is this a v0 requirement or a nice-to-have?

If hard → drop to "all code links reuse the same tab" for v0.

### Q4: nav tree refresh trigger

After `git clone`, does the nav tree auto-refresh? LightningFS has no watcher. Options:
* poll IDB on interval (wasteful)
* explicit refresh button
* terminal emits an event after git commands complete (shell hook)
* nav tree re-reads on tab switch (side panel becomes visible)

This affects L1 and L6. Tests need to know what triggers the refresh.

### Q5: fixture repo ownership

Who creates `nap-test-main` and `nap-test-nap` on GitHub? What org? Public or needs PAT?

Recommend: public repos under the project org. TE creates and maintains them. Content is deterministic — specific files at specific line numbers with marker comments that tests assert against.
