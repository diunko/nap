# v0 — test architecture

Strategic test cases for the seams. Not unit tests for obvious things.

## Test infrastructure

**Playwright fixture** — Chrome launched with `--load-extension=dist/`, navigates to `chrome-extension://{id}/side-panel.html`. Loses the side panel frame but tests the app in isolation. The bash-poc `cmd()` helper (prompt-counting) carries forward unchanged.

**Fixture repo** — real small public repo with .nap/ structure: `20-architects/001-architect/` (prompt.md), `30-napkins/0100-feature/` (.napkin.nap.json status "doing", agents/), `30-napkins/0200-other/` (status "backlog"), numbered .md chapters. Needed by every medium test that involves clone + nav tree.

**LFS store name** — `'nap-ext'` (stable across panel reloads, per spec).

## Seam 1: Monaco in extension sandbox

The scariest unknown. If Monaco can't boot, everything stalls.

### T1.1 — Monaco boots, no CSP errors (medium)

* **flow:** load side-panel.html → wait for Monaco editor DOM → collect console errors
* **subsystems:** Monaco, extension CSP, Web Worker loading, `MonacoEnvironment.getWorkerUrl`
* **expected:** `.monaco-editor` element visible, zero console messages containing "Content Security Policy" or "worker"
* **where it breaks:** blob: URL blocked by CSP → worker fails → Monaco never initializes. The fix (bundle editor.worker.js as extension asset + `getWorkerUrl`) may itself fail if the bundled path is wrong or the manifest doesn't serve it.
* **test size:** medium — needs real Chrome extension runtime
* **verification:** `page.waitForSelector('.monaco-editor')` + assert console error collector is empty for CSP/worker patterns

### T1.2 — napkin-markdown tokenizer registered (medium)

* **flow:** Monaco boots → create model with language `napkin-markdown` → type `# heading` and `//DU: comment`
* **subsystems:** Monaco, `registerNapkinMarkdown()`, tokenizer rules
* **expected:** tokens get correct scopes (heading, comment.role). The monarch tokenizer is wired up.
* **where it breaks:** `registerNapkinMarkdown()` not called before editor creation, or language ID mismatch between registration and model creation.
* **test size:** medium — monarch tokenizer only runs in Monaco's real runtime
* **verification:** use `monaco.editor.tokenize()` exposed on window, or check that heading line has the `heading` token class in the DOM (`.mtk` spans)

## Seam 2: Monaco read/write LightningFS

Probably straightforward (both async, both work with strings). But never tested together.

### T2.1 — file → Monaco model (medium)

* **flow:** write a .md file to LFS via `lfs.promises.writeFile` (through page.evaluate) → trigger "open file" in editor → read Monaco model value
* **subsystems:** LightningFS IDB, Monaco `createModel`, file-to-model wiring
* **expected:** `editor.getModel().getValue()` matches written file content exactly (including newlines, UTF-8)
* **where it breaks:** encoding mismatch (Uint8Array vs string), readFile returning buffer when Monaco expects string, path mismatch between nav tree click and LFS read path.
* **test size:** medium
* **verification:** `page.evaluate(() => window.__editor.getModel().getValue())` compared to known content

### T2.2 — edit → debounced auto-save → LFS (medium)

* **flow:** file open in editor → type new content → wait debounce interval → read file from LFS
* **subsystems:** Monaco onChange, debounce timer, `lfs.promises.writeFile`
* **expected:** LFS file content matches editor content after debounce settles
* **where it breaks:** debounce never fires (event not wired), writeFile path doesn't match readFile path, auto-save writes to wrong location.
* **test size:** medium
* **verification:** type in editor via Playwright keyboard, wait debounce + margin, `page.evaluate(() => window.__lfs.promises.readFile(path, 'utf8'))`, compare

## Seam 3: Terminal ↔ LightningFS ↔ Editor (bidirectional)

The glue test. One LFS instance, three consumers. If this works, the architecture holds.

### T3.1 — editor write → terminal reads (medium)

* **flow:** open chapter in editor → type `// review note` → wait auto-save → switch to terminal → `cat <filepath>` → output includes `// review note`
* **subsystems:** Monaco, auto-save, LightningFS, terminal/BashShell, fs-adapter readFile
* **expected:** cat output contains the editor-written text
* **where it breaks:** auto-save didn't flush before cat, fs-adapter reads from a different LFS instance (would mean the "single instance" contract is broken), path mismatch (editor saves to `/home/user/repo/.nap/...` but cat uses different path).
* **test size:** medium
* **verification:** extend cmd() helper — type in editor, wait, cmd('cat <path>', '// review note')

### T3.2 — terminal write → editor reads (medium)

* **flow:** terminal `echo "// terminal note" >> <filepath>` → open/reopen file in editor → Monaco model includes appended text
* **subsystems:** terminal echo/append, LightningFS writeFile (via fs-adapter appendFile), Monaco model reload
* **expected:** editor content includes `// terminal note`
* **where it breaks:** Monaco model created from LFS on open but never refreshed. If file was already open, the model holds stale state. This is the real question: does the editor reload from LFS on tab activation, or only on first open?
* **test size:** medium
* **verification:** cmd() echo, then trigger file re-open (click nav tree or switch tabs), read model value. Two variants: (a) file not yet open — proves first-open path, (b) file already open — proves refresh-on-focus path. If (b) fails, that's a design decision the implementer needs to make, and this test surfaces it early.

## Seam 4: Nav tree ↔ LightningFS

### T4.1 — directory convention parsing (small)

* **flow:** given a directory listing + .napkin.nap.json contents → parse to tree model
* **subsystems:** nav tree parser (pure function)
* **expected:**
  * `20-architects/001-architect/` → architects section, entry "001-architect", children: prompt.md, scratch/
  * `30-napkins/0100-feature/` → napkins section, entry "0100-feature", status label "doing"
  * `30-napkins/0200-other/` → napkins section, entry "0200-other", status label "backlog"
  * agents under napkin: `agents/001-test-arch-feature/` → nested under 0100-feature
  * `10-docs/`, `15-feedback/` → own sections
* **where it breaks:** numeric prefix regex off-by-one, .napkin.nap.json missing or malformed (no status field), agent directory not nested under parent napkin.
* **test size:** small — pure logic, vitest, no browser
* **verification:** call parser with mock directory listing, assert tree structure

### T4.2 — numeric sort order (small)

* **flow:** entries [0200-other, 0100-feature, 0300-late] → sorted [0100, 0200, 0300]
* **subsystems:** sort comparator
* **expected:** numeric prefix determines order, not lexicographic string sort (which would also work here, but edge case: 10 vs 2 would differ)
* **where it breaks:** string sort vs numeric sort — matters if prefixes have different digit counts (agents: 001, 002 vs napkins: 0100, 0200).
* **test size:** small
* **verification:** assert sorted array order

### T4.3 — nav tree reflects cloned repo (medium)

* **flow:** git clone fixture repo in terminal → nav tree DOM shows correct sections
* **subsystems:** terminal, isomorphic-git, LightningFS, nav tree parser, nav tree render
* **expected:** architects and napkins sections visible, status labels present, entries expandable
* **where it breaks:** nav tree doesn't re-read after clone (no watch/poll), readdir path is wrong (missing the cloned repo name prefix), .napkin.nap.json not found because path construction omits a segment.
* **test size:** medium
* **verification:** cmd() clone, then assert nav tree DOM contains expected section headers and entry names. If nav tree doesn't auto-refresh, test should document: "requires manual trigger or panel reload after clone."

## Seam 5: Link routing

Two-repo architecture makes this non-trivial. The .nap repo is cloned locally; file:line links point to the MAIN CODE REPO on GitHub.

### T5.1 — file:line → GitHub blob URL construction (small)

* **flow:** given href `/modules/server/copy_document.ts#L51` + known main repo `{owner}/{repo}/{branch}` → construct `https://github.com/{owner}/{repo}/blob/{branch}/modules/server/copy_document.ts#L51`
* **subsystems:** link parser (parseLinkHref from v3), GitHub URL builder (NEW — doesn't exist in v3)
* **expected:** correct GitHub URL with owner/repo from main code repo, NOT from .nap repo
* **where it breaks:** using cloned .nap repo's origin as owner/repo (wrong repo!), forgetting to strip leading `/` before appending to blob URL, `#L` anchor format mismatch.
* **test size:** small — pure function, vitest
* **verification:** assert URL string for multiple cases:
  * absolute path with `#L` anchor
  * path with `:line` suffix (colon style)
  * bare filename (should it resolve? probably error or best-effort)
  * .ts/.tsx extensions → GitHub blob

### T5.2 — .md link → opens in editor from IDB (small + medium)

* **flow:** link href `02-id-universe.md` in chapter `01-copy-pipeline.md` → resolved to sibling path → editor loads from LFS
* **subsystems:** routeLink (v3 reuse), LightningFS read, Monaco model creation
* **small verification:** routeLink returns `{ action: 'openDoc', path: '<resolved>' }` — vitest
* **medium verification:** Cmd+click on .md link in Monaco → editor loads correct file content
* **where it breaks:** relative path resolution wrong (dirname of source file incorrect), file doesn't exist in LFS (path off by one directory level).

### T5.3 — https:// → new tab (small)

* **flow:** link `https://example.com` → classified as external
* **subsystems:** routeLink classification
* **expected:** `{ action: 'openExternal', url: 'https://example.com' }`
* **where it breaks:** unlikely — simple prefix check. Include for completeness but low priority.
* **test size:** small
* **verification:** assert routeLink output

### T5.4 — Cmd+click dispatches to correct target (medium)

* **flow:** editor showing chapter with three link types → Cmd+click each → correct behavior
* **subsystems:** Monaco link provider, click handler, content script (for GitHub navigation), chrome.tabs API
* **expected:** code link → main tab navigates to GitHub, .md link → editor loads new file, https → new tab opens
* **where it breaks:** Monaco's link detection not wired up (no `registerLinkProvider`), Cmd+click not intercepted, content script not receiving message from side panel, `chrome.tabs.update` permissions missing.
* **test size:** medium
* **verification:** this is the hardest to test in isolation (chrome-extension:// page loses side panel frame). May need to verify at the function level — simulate click context, assert the right API was called — rather than true end-to-end Cmd+click. Content script communication is the real seam to test here.

## Seam 6: Git flow in extension context

Proven in bash-poc but needs re-proving because: different LFS store name, extension runtime, shared instance with editor/nav.

### T6.1 — clone → nav tree populates (medium)

* **flow:** terminal `git clone <fixture-repo>` → nav tree shows .nap structure
* **subsystems:** terminal, isomorphic-git (CORS proxy), LightningFS, nav tree
* **expected:** clone succeeds (terminal shows "done."), nav tree sections appear
* **where it breaks:** CORS proxy blocked by extension CSP (unlikely but check manifest), Buffer polyfill missing, LFS store name mismatch between terminal and nav tree.
* **test size:** medium
* **verification:** cmd() clone + nav tree DOM assertions. This is the "first five minutes" test — if it fails, nothing else works.

### T6.2 — edit via editor → git status shows modified (medium)

* **flow:** clone → open file in editor → edit → auto-save → terminal `git status` → shows modified
* **subsystems:** editor, auto-save, LightningFS, isomorphic-git statusMatrix
* **expected:** `git status` output contains "modified" and the filename
* **where it breaks:** auto-save writes to wrong path relative to git repo root, isomorphic-git computes status from HEAD but LFS file is at a different path, the statusMatrix dir doesn't match the LFS write path.
* **test size:** medium
* **verification:** edit in Monaco, wait, cmd('git status', 'modified')

### T6.3 — full commit cycle (medium)

* **flow:** edit → `git add .` → `git commit -m "msg"` → `git log --oneline -1` shows "msg"
* **subsystems:** terminal, isomorphic-git add/commit/log, LightningFS
* **expected:** commit succeeds, log shows message
* **where it breaks:** already proven in bash-poc. Re-test here to verify the shared LFS instance doesn't cause issues (e.g., editor's auto-save writing during add/commit creates race).
* **test size:** medium
* **verification:** cmd() sequence, same pattern as bash-poc Story 4

## Seam 7: Theme application

### T7.1 — CSS variable generation from ThemeDef (small)

* **flow:** given lightBlue ThemeDef → generate CSS variables
* **subsystems:** theme application logic (camelToKebab + setProperty)
* **expected:** `--nap-bg: #f0f4f8`, `--nap-text: #2e3440`, etc.
* **where it breaks:** camelToKebab produces wrong variable name, shell key naming convention changes.
* **test size:** small — vitest, pure function
* **verification:** call the CSS variable generator, assert key-value pairs

### T7.2 — theme visually applied on panel load (medium)

* **flow:** load side-panel.html → check computed styles
* **subsystems:** theme registration, `applyTheme()`, CSS variables on root
* **expected:** editor background is `#f0f4f8`, `--nap-bg` resolves to `#f0f4f8`
* **where it breaks:** `applyTheme()` not called at startup, Monaco theme not registered before editor creation (throws), CSS variables set on wrong element.
* **test size:** medium
* **verification:** `page.evaluate(() => getComputedStyle(document.documentElement).getPropertyValue('--nap-bg'))` returns `#f0f4f8`

## Seam 8: Panel lifecycle

### T8.1 — panel survives main tab navigation (medium)

* **flow:** panel open with cloned repo + file in editor → navigate main tab to different URL → check panel state
* **subsystems:** Chrome side panel lifecycle, IDB persistence, Monaco state
* **expected:** editor content preserved, nav tree intact, terminal history present
* **where it breaks:** panel DOM re-created on tab navigation (Chrome behavior), IDB persists but in-memory state (Monaco models, terminal history) lost. This test reveals whether the panel stays alive or gets destroyed/recreated.
* **test size:** medium
* **verification:** navigate main tab, then read editor model value and check nav tree DOM. NOTE: may not be testable via chrome-extension:// URL approach (no real side panel frame). Document as "manual verification required" if so.

## Test priority

**Prove first (gate everything else):**
1. T1.1 — Monaco boots (if this fails, stop)
2. T2.1 — LFS → Monaco model (if this fails, no editor)
3. T2.2 — edit → auto-save → LFS (if this fails, no persistence)

**Prove second (core loops):**
4. T3.1 — editor → terminal (bidirectional glue)
5. T3.2 — terminal → editor (bidirectional glue)
6. T6.1 — clone → nav tree (first-run experience)

**Prove third (features):**
7. T4.3 — nav tree reflects repo structure
8. T6.2 — edit → git status
9. T5.4 — Cmd+click dispatches correctly
10. T1.2 — tokenizer active

**Small tests (run always, fast):**
- T4.1, T4.2, T5.1, T5.2 (small part), T5.3, T7.1

## Patterns to extend from bash-poc

The `cmd()` helper from `packages/bash-poc/e2e/tests/terminal.spec.ts` is the foundation:

* **prompt counting** — count `$ ` occurrences before and after command, wait for increment. Reliable, no sleep.
* **output extraction** — find `$ <command>` in terminal text, slice between that and next `$ `. Clean.
* **waitFor assertion** — optional string or regex match on output.
* **clone helper** — dedicated `cloneRepo()` with 60s timeout for network.

**New helpers needed for extension tests:**

* `editorContent()` — `page.evaluate(() => window.__editor?.getModel()?.getValue())`
* `editorType(text)` — focus editor + keyboard.type, respecting Monaco's input handling
* `lfsRead(path)` — `page.evaluate((p) => window.__lfs.promises.readFile(p, 'utf8'), path)`
* `lfsWrite(path, content)` — `page.evaluate(...)` for test setup (pre-populate files)
* `navTreeEntries()` — read nav tree DOM structure for assertions
* `waitForAutoSave()` — wait debounce interval + margin (not a sleep — poll LFS until content matches)

**Extension-specific fixture setup:**

```typescript
// Get extension ID from chrome://extensions or from the loaded extension path
const extId = await getExtensionId(context);
await page.goto(`chrome-extension://${extId}/side-panel.html`);
// Wait for Monaco + terminal to initialize
await page.waitForSelector('.monaco-editor');
await page.waitForSelector('.wterm');
```
