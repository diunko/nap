# v0 — UX test

## Why this exists

47 tests pass. The extension doesn't work when a human uses it.

Every test bypasses the actual user interface:
- `window.__refreshNavTree()` instead of nav tree auto-refreshing after clone
- `window.__openFile(path)` instead of clicking a file in the nav tree
- `window.__triggerLink(href)` instead of Cmd+clicking a link in Monaco
- `window.__setMainRepoConfig()` instead of any user-reachable settings

The tests prove internal wiring works. They don't prove the user can use the extension. This is the test that does.

---

## The test: E2E-UX-1 — first-time user installs extension and reads a .nap repo

One test. Does exactly what a human does after installing. No `window.__` hooks except where Playwright physically cannot simulate the interaction (justified below).

### Prerequisites

- Fixture repos exist on GitHub:
  - `diunko/nap-test-main` — the code repo (never cloned, only linked)
  - `diunko/nap-test-nap` — the .nap repo (cloned by user)
- `nap-test-nap` has chapters with file:line links pointing to `nap-test-main`
- Extension built to `dist/`

### Setup (acceptable automation)

```typescript
// Launch chrome with extension — same as all medium tests
const context = await chromium.launchPersistentContext('', {
  channel: 'chromium',
  args: [
    `--disable-extensions-except=${pathToExtension}`,
    `--load-extension=${pathToExtension}`,
    '--disable-blink-features=AutomationControlled',
  ],
});
```

### Step 1: navigate to the code repo on GitHub

```typescript
const ghPage = await openGitHub(context, 'https://github.com/diunko/nap-test-main');
```

**User action:** types github.com/diunko/nap-test-main in browser.
**Acceptable to automate:** yes — navigating to a URL isn't a UX seam.

### Step 2: open side panel

```typescript
const panel = await openSidePanel(context, ghPage, extensionId);
```

**User action:** clicks extension icon in toolbar.
**What the test does:** clicks the hidden trigger button, which sends `chrome.runtime.sendMessage({ type: 'open_side_panel' })` → background calls `chrome.sidePanel.open()`. This is the same codepath as clicking the extension icon (both go through `openPanelOnActionClick`).
**Acceptable to fake:** yes — Playwright can't click browser chrome. The trigger button exercises the same sidePanel.open() path.

### Step 3: set main-repo config

**This is the first UX gap.** There is currently no user-reachable way to set this.

The manifest has `"default_popup": "popup.html"` but also `openPanelOnActionClick: true` in background.ts. These conflict — clicking the extension icon opens the side panel, not the popup. The settings UI is unreachable.

**What the test SHOULD do:**

```typescript
// Open settings within the side panel (gear icon or "settings" link)
await panel.locator('#settings-btn').click();

// Fill in main repo
await panel.locator('#main-repo-input').fill('diunko/nap-test-main');
await panel.locator('#main-branch-input').fill('main');
await panel.locator('#settings-save').click();

// Close settings, back to terminal
await panel.locator('#settings-close').click();
```

**What must change in the extension:** move settings INTO the side panel. A gear icon in the tab bar or nav header. Opens an inline settings form. Saves to `chrome.storage.sync`. The popup.html can stay as a fallback for right-click → "Options", but the primary path must be inside the panel.

**NOT acceptable to fake.** This is the #1 UX failure. The test must exercise a real user-facing settings path.

### Step 4: clone the .nap repo in terminal

```typescript
// Terminal should be the default active tab
await expect(panel.locator('.wterm')).toContainText('$', { timeout: 10_000 });

// Type the clone command
await panel.locator('.wterm').click();
await panel.keyboard.type('git clone https://github.com/diunko/nap-test-nap', { delay: 5 });
await panel.keyboard.press('Enter');

// Wait for clone to finish (new prompt appears)
await expect(async () => {
  const text = await panel.locator('.wterm').textContent() ?? '';
  expect(text).toContain('done.');
}).toPass({ timeout: 60_000 });
```

**User action:** types git clone command, presses Enter.
**Real interaction:** yes — keyboard.type + keyboard.press is what the user does. The cmd() helper with prompt counting is fine here — it's testing terminal behavior, not bypassing it.

### Step 5: nav tree auto-populates — NO manual refresh

```typescript
// Nav tree should auto-populate after clone completes
// Give it a reasonable window — the nav tree should detect the clone finished
await expect(panel.locator('#nav-tree')).not.toBeEmpty({ timeout: 5_000 });

// Verify structure
const navText = await panel.locator('#nav-tree').textContent();
expect(navText).toContain('napkins');
```

**User action:** waits. Looks at the nav tree. Expects it to populate.
**NOT acceptable to fake.** This is bug #1 from the field report. The test MUST NOT call `window.__refreshNavTree()`. If the nav tree doesn't auto-populate, the test fails. That's the point.

**What must change in the extension:** git clone must trigger nav tree refresh. Options:
- Shell emits a custom event after git commands (best — git clone, git pull, git checkout all trigger it)
- BashShell has an `onCommandComplete` callback that checks if the command was `git` and calls `refreshNavTree()`
- Simpler: after any command completes, check if repos exist in `/home/user/` that aren't yet in the nav tree, and refresh if so

### Step 6: click a chapter file in the nav tree — real DOM click

```typescript
// Find the chapter file in the nav tree
// The nav tree renders .nav-file elements with the display name as textContent
const chapterFile = panel.locator('.nav-file', { hasText: '01-copy-pipeline.md' });
await expect(chapterFile).toBeVisible({ timeout: 3_000 });

// May need to expand parent sections first
const napkinsSection = panel.locator('.nav-entry', { hasText: '0100-feature' });
if (await napkinsSection.isVisible()) {
  // Click to expand if collapsed
  const children = napkinsSection.locator('~ .nav-children');
  if (await children.evaluate(el => el.classList.contains('collapsed'))) {
    await napkinsSection.click();
  }
}

// Click the chapter file
await chapterFile.click();
```

**User action:** clicks the file name in the nav tree.
**Real interaction:** yes — this is a DOM click on a real rendered element. The nav tree's click handler calls `openFile()` internally, which is correct.
**NOT acceptable to fake.** The test must click the actual nav tree element. `window.__openFile()` bypasses the nav tree entirely — it doesn't prove the nav tree is clickable or that the click handler is wired.

### Step 7: verify editor shows chapter with napkin-markdown styling

```typescript
// Tab should have switched to editor
await expect(panel.locator('.tab[data-tab="editor"]')).toHaveClass(/active/, { timeout: 2_000 });

// Editor should show the chapter content
const content = await panel.evaluate(() => window.__editor?.getModel()?.getValue() ?? '');
expect(content).toContain('Copy Pipeline');
expect(content).toContain('copy_document.ts');
```

**Acceptable to read model value:** yes — there's no user-visible way to "read" editor content in Playwright. The user reads with their eyes; we read with `getModel().getValue()`. This isn't a bypass — it's the only way to assert content.

**Optional visual check:** verify tokenizer is active by checking for `.mtk` spans with expected classes in the editor DOM. But this is secondary — the content being there is what matters.

### Step 8: Cmd+click a file:line link in the editor

**This is the hardest step.** Monaco's Cmd+click on links works through:
1. User holds Cmd/Ctrl and hovers over a link → Monaco underlines it
2. User clicks → Monaco calls `resolveLink()` on the link provider
3. `resolveLink()` routes the link (openCode → navigateGitHubTab)

Playwright can simulate Cmd+click, but the link must be detected by Monaco's link provider first.

```typescript
// Find the line containing the file:line link
const linkLine = await panel.evaluate(() => {
  const model = window.__editor.getModel()!;
  const content = model.getValue();
  const lines = content.split('\n');
  for (let i = 0; i < lines.length; i++) {
    if (lines[i].includes('copy_document.ts')) return i + 1; // 1-indexed
  }
  return -1;
});
expect(linkLine).toBeGreaterThan(0);

// Click on the link text with Cmd held
// Monaco needs the click to land on the actual link range
const editorEl = panel.locator('.monaco-editor .view-lines');

// Use Monaco's action as the trigger — this is what Cmd+click actually invokes
await panel.evaluate(() => {
  // Position cursor on the link
  const model = window.__editor.getModel()!;
  const content = model.getValue();
  const lines = content.split('\n');
  for (let i = 0; i < lines.length; i++) {
    const linkMatch = lines[i].match(/\[([^\]]+)\]\(([^)]+)\)/);
    if (linkMatch && linkMatch[2].includes('copy_document.ts')) {
      // Position cursor inside the link href
      const col = lines[i].indexOf(linkMatch[2]) + 1;
      window.__editor.setPosition({ lineNumber: i + 1, column: col });
      break;
    }
  }
  // Trigger Monaco's openLink action — this is what Cmd+click invokes internally
  window.__editor.getAction('editor.action.openLink')?.run();
});
```

**Acceptable to use editor.action.openLink:** yes, with justification. Cmd+click in Monaco triggers `editor.action.openLink` on the link under the cursor. Playwright can't reliably simulate Cmd+hover (which triggers link decoration) + Cmd+click (which must land on the decorated link range with pixel precision). Using `setPosition` + `editor.action.openLink` exercises the same code path: cursor on link → resolveLink called → route dispatched → navigateGitHubTab called.

**What would NOT be acceptable:** calling `window.__triggerLink(href)` — that bypasses Monaco's link provider entirely, doesn't test link detection, doesn't test resolveLink, doesn't test the provider → router → navigator chain.

**The key difference:** `editor.action.openLink` starts at "cursor is on a link, user activated it" and runs through the link provider's `resolveLink()`. `window.__triggerLink` starts at "here's an href, route it" and skips the entire Monaco layer.

### Step 9: verify GitHub tab navigated to correct URL


**User action:** looks at the main tab, sees it navigated to the right file on GitHub.
**Real interaction:** yes — we're checking the actual browser URL.

## What's acceptable to fake vs what MUST be real

| Step | Interaction | Real or fake? | Why |
|------|-----------|---------------|-----|
| 1. Navigate to github.com | `page.goto()` | Automated OK | Not a UX seam |
| 2. Open side panel | Trigger button | Fake OK | Can't click browser chrome; same sidePanel.open() codepath |
| 3. Set main-repo config | Click settings UI in panel | **MUST be real** | Currently broken — no user path exists |
| 4. Clone repo | keyboard.type + Enter | Real | Terminal interaction is the user's actual action |
| 5. Nav tree populates | Wait for DOM | **MUST be real** | Bug #1 — auto-refresh is broken |
| 6. Click chapter in nav tree | DOM click on .nav-file | **MUST be real** | Proves nav tree is interactive, not just rendered |
| 7. Read editor content | getModel().getValue() | Read OK | No other way to assert content programmatically |
| 8. Activate link | setPosition + editor.action.openLink | Acceptable | Exercises resolveLink chain; Cmd+hover+click can't be reliably simulated |
| 9. Check GitHub URL | ghPage.url() | Real | Actual browser state |

## UX gaps this test exposes (beyond the 3 reported bugs)

### Gap 1: settings unreachable (reported)

`openPanelOnActionClick: true` in background.ts means clicking the extension icon opens the side panel, not popup.html. The settings form exists but the user can't get to it.

**Fix:** add a settings surface inside the side panel. Gear icon in the tab bar header area. Opens inline. Popup.html becomes the right-click → "Options" fallback only.

### Gap 2: nav tree doesn't auto-refresh after clone (reported)

Git clone completes, nav tree stays empty. User stares at blank nav.

**Fix:** BashShell needs an `onCommandComplete` callback. When the completed command starts with `git clone` or `git pull` or `git checkout`, call `refreshNavTree()`. Alternatively, any command that exits code 0 checks if new repos appeared in `/home/user/`.

### Gap 3: Cmd+click on links may not work (reported)

The link provider is registered on `'napkin-markdown'` language. The editor creates models with `language: 'napkin-markdown'` in the initial config (side-panel.ts:94). But `openFile()` at line 214-219 does `model.setValue(content)` on the existing model — so the language should be correct.

The likely failure: Monaco's link provider `provideLinks` returns links, but `resolveLink` sets `link.url = undefined` for internal routes (openDoc, openCode) at lines 562 and 566. Setting url to `undefined` after Monaco already set it to the href string may cause Monaco to treat the link as "no destination" and not fire the click handler.

**Fix:** for openCode links, set `link.url` to the GitHub URL string (let Monaco open it). For openDoc links, the `resolveLink` function should call `openFile()` AND return the link with url set to something (even a `javascript:void(0)` or `#`) so Monaco considers the resolve successful.

Alternative: instead of using Monaco's link provider for click handling, register a separate click handler via `editor.onMouseDown` that checks for Cmd+click, finds the link at the click position, and routes it. This is more reliable than fighting with Monaco's link provider semantics.

### Gap 4: no feedback when main-repo config is missing

If the user clicks a file:line link before setting main-repo config, the URL resolves to `https://github.com/OWNER/REPO/blob/main/...` — a 404. No error message, no prompt to configure.

**Fix:** when `mainRepoConfig` is undefined and a code link is clicked, show an inline notification: "Set your main code repo in settings to enable code links." Link to the settings gear.

### Gap 5: no visual indication of auto-save state

User edits in Monaco but has no way to know if the file was saved. No "saving...", no "saved", no dirty dot on the tab.

**Fix (minimal for v0):** add a small status indicator. Even just a dot in the tab bar that appears on edit and disappears after auto-save completes.

### Gap 6: manifest popup vs side panel conflict

The manifest declares both `"default_popup": "popup.html"` and the background sets `openPanelOnActionClick: true`. The behavior depends on which one Chrome processes last. This is fragile.

**Fix:** remove `"default_popup"` from manifest.json. Move settings into the side panel (gap 1). Register popup.html as the options page instead:
```json
"options_ui": {
  "page": "popup.html",
  "open_in_tab": false
}
```
This makes it accessible via right-click → "Options" without conflicting with side panel toggle.

### Gap 7: nav tree sections might need expanding before files are clickable

The nav tree renders sections collapsed by default. After clone, user sees "napkins" but the chapter files might be hidden inside collapsed sections. User needs to click to expand 0100-feature, then see the chapter files.

**Not a bug** — expected tree behavior. But the test needs to handle it (expand sections before clicking files).
